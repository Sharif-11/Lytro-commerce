# Lytronix Multi-Tenant Commerce Platform — Detailed Software Requirements Specification

Version 1.0 draft · updated 2026-10-03 · companion to `SRS.md` (overview). This document lists every functional requirement individually so an end-to-end (E2E) test plan can be written against it. **Requirement IDs in this document are the authoritative ones for test traceability.**

## 0. How to read this document

**Requirement rows.** Every requirement is one row: `ID | Requirement | Pass criteria | Pri | Ver`.

- **ID:** module prefix plus number, never reused. A retired requirement keeps its ID and is marked *Withdrawn*.
- **Requirement:** one testable obligation, written with "shall".
- **Pass criteria:** the observable result that makes the test pass, with concrete values where they are decided.
- **Pri:** `M` must be present at launch, `S` should, `C` could (later).
- **Ver:** how it is verified: `E2E` browser or dashboard flow, `API` HTTP-level check, `JOB` scheduled-job or time-based check, `LOAD` load or performance test, `MAN` inspection or review.

**Values in [square brackets]** are defaults chosen for this draft that were not explicitly decided; they must be confirmed and are all editable settings. Values without brackets were decided in design discussions. The full list of items to confirm is in section 25.

**Time.** All day boundaries use the Asia/Dhaka time zone. Times are stored in UTC.

**Scope of "the platform".** The server (API, jobs), the tenant dashboard (web app, installable PWA), the operator console, and a shared, tenant-branded storefront (section 14.2) served for every tenant by default. A tenant with its own website may switch the shared storefront off and use only the API and the hosted payment page.

| Actor | Description |

### 2.6 Error contract

Every API error is JSON `{ "error": { "code": "...", "message": "...", "details": {} } }`. Added 2026-10-02 — the three fields have deliberately different rules:

- **`code`** is a stable, machine-readable identifier (e.g. `validation_error`) and is never translated or reworded, in any environment — API integrators write code against this string, so it follows the same never-break-a-version discipline as API-14; only `message` changes with language.
- **`message`** is a short, non-technical sentence meant for a human to read (a tenant's staff member, or an end user of a tenant's own integration) — never a raw exception message, a library error, or anything implying internal implementation. It is localized per I18N-01's platform-wide rule: Bangla by default, English when the request's `Accept-Language` header requests it. Field-level validation specifics belong in `details`, not prose stuffed into `message`.
- **`details`** carries structured, field-level data (which field, what was wrong) — never a stack trace, never an internal file path, never a raw database or third-party-provider error string.
- **Stack traces and internal exception detail are never part of any API response outside a non-production environment** (SEC-16 makes this a formal, security-relevant requirement, not just a style note).

Defaults [to confirm]:

| HTTP | code | Meaning |
| --- | --- | --- |
| 400 | `validation_error` | Missing or malformed input |
| 401 | `unauthenticated` | No or invalid credentials |
| 403 | `forbidden` | Authenticated but lacks the permission or scope |
| 403 | `plan_limit_reached` | A count or size limit of the plan is reached (products, seats, storage) |
| 403 | `plan_feature_unavailable` | The plan does not include the feature |
| 403 | `tenant_offline` | The tenant is read-only, locked, archived or suspended for the requested action |
| 404 | `not_found` | Not found, or belongs to another tenant |
| 409 | `conflict` | Duplicate or state conflict |
| 429 | `rate_limited` | Per-minute limit; carries `Retry-After` |
| 429 | `quota_exceeded` | Monthly quota reached |
| 503 | `service_unavailable` | A required outside service (such as the SMS provider) could not be reached, so the action did not complete. Carries `Retry-After` when a retry time is known. Added 2026-10-04 |

### 7.2 Pay-as-you-go tenants (PYG)

## 9. Upgrade — cycle restarts (UPG)

Rule: the new plan starts at confirmation, the tenant gets credit for the unused part of the old plan, pays the new price minus that credit, and the billing cycle restarts. Worked examples used in the pass criteria:

- **Example A.** Starter 1-month (449 TK, 30 days), upgrade to Growth 1-month (699 TK) with 20 days remaining: credit = 449 × 20 / 30 = 299.33 → **299**; amount due = 699 − 299 = **400**.
- **Example B.** Starter 12-month (4,741 TK, 365 days), upgrade to Growth 12-month (7,381 TK) with 265 days remaining: credit = 4,741 × 265 / 365 = 3,442.10 → **3,442**; amount due = 7,381 − 3,442 = **3,939**.

**Open points for this section**

- Decided: KYC records and images are deleted with the tenant at day 60 (KYC-10, LIF-19, DAT-15). They are not kept under the subscriber, so a returning owner must submit again.
- Backup copies of KYC data fall under LIF-22 and DAT-30 like any other deleted data, so they leave backups within 30 days. This needs legal confirmation with the rest of LIF-22.
- Whether `verified` gates payouts or withdrawals is not decided. The tenant status (KYC-16) is recorded but no feature depends on it yet.
- `kyc:review` is a new operator permission; it needs adding to the permission list in section 5 and the operator roles in the console.
- Legal basis, consent wording and the data-protection regime applicable in Bangladesh need legal review before launch.

### 24.4 Redis and shared counters (RED)

Decided 2026-10-02 (supersedes the independent-per-server design below OD-38 previously proposed): every application server (one at launch, more from phase 2/3) shares one Redis (or Valkey) instance, running on its own dedicated small VPS (DAT-19) reached over a private tunnel (WireGuard, the same pattern as DAT-21's replication link), never on an application or database server. This is a deliberate, accepted single point of failure, the same risk framing as DAT-7a's single-database-server phase: chosen over the cost and operational overhead of a fourth/fifth server for Redis replication at launch scale, and safe to accept specifically because RED-05's in-process fallback already exists as a complete, tested degrade path for a total Redis outage. A shared instance also removes the need for dividing limits across healthy servers — general API rate limits are now true, exact, global counters in the one Redis instance, with no server-count math involved.

### 24.6 Scaling roadmap and future-proofing (SCL)

The design is sized in stages (a back-of-envelope model, SCL-01) and needs no rewrite up to about 5,000 tenants; beyond about 10,000 the platform is split into independent cells, which is a structural change and not a rewrite, provided the seams below exist from launch. The binding limits, in order, are the database's hot working set against RAM, backup restore time against the recovery objective, and operating effort; CPU and write throughput are not limiting within this range.

| Tenants | Topology and changes |
| --- | --- |
| Under 100 | One primary server; standby added at about 30 tenants (DAT-55). |
| Under 500 | Primary and standby; read pool on the standby; resize to 8 vCPU / 16 GB. |
| Under 2,000 | Database servers separated from 2–3 stateless application servers; connection pooler, monthly partitioning of large append-only tables, the full observability stack, notification worker on its own server, shared Redis. |
| Under 5,000 | Replica fleet with lag-aware routing; cold-order archiving; a lightweight search engine if CCH-12's threshold is crossed; larger network port; managed PostgreSQL reconsidered. |
| Under 10,000 | Decision point between one very large primary and cells; reliance on standby promotion because restore-from-backup time exceeds the recovery objective (SCL-04). |
| 10,000 and over | Cells: independent stacks of about 2,000–3,000 tenants each, a small control-plane database, host-to-cell routing, a message broker in place of the PostgreSQL job queue, a separate analytics store. |

**Reading the table against SCL-04 (restore time versus the recovery objective):** the projected restore time crosses 70% of the stated 4-hour recovery objective (DAT-54) somewhere in the "under 10,000" tier (at about 2.8 h against a 4 h target), which is exactly why that tier is the decision point between one very large primary and cells, and why SCL-04's alert exists rather than relying on eyeballing this table as tenants grow.

**Sensitivity, since every figure above scales with the two least-certain inputs:** a tenant base that is 3x busier (about 1,000 orders/tenant/month) shifts every row up by roughly that factor and pulls each tier boundary in three years earlier than shown; a base that is 3x quieter pushes them out by about the same. Traffic is also expected to be skewed rather than even — a small share of tenants may generate a large share of load — which is what SCL-14's per-tenant load alert and the Enterprise/dedicated-cell options exist to absorb, on top of the model's assumption of a uniform average tenant. Non-database limits (SMS provider throughput, AI provider quota, Cloudflare custom-hostname and Worker charges, courier/wallet API limits) are not shown in this table and are covered separately by SCL-12's per-tier checklist.

### 26.3 Test environment and data

- **Tenants:** at least one in each of trial, Starter, Growth, Pro, and one for each lapsed state (grace, read-only, locked, archived).

- **Doubles for external systems:** SMS provider stub (records parts, returns delivery reports and forced failures); a courier stub (the `steadfast-mock` project beside the main repository is the starting point); bKash sandbox or a stub; AI provider stub with forced failures; a listener-phone simulator that posts sample receipts (matching, mismatching, duplicate, unknown sender); a receiver for outgoing webhooks that can return errors.
- **Files:** images of 100 KB, 4 MB, 6 MB and a fake `.jpg` executable; videos of 50 MB and 101 MB; used for storage and upload tests.
- **Accounts:** an operator account with two-factor; two tenants with overlapping data (same product names, same order numbers) for isolation tests.
- **Concurrency helpers:** tools to send N simultaneous requests for balance, order number, stock, idempotency and session tests.

### 26.4 Traceability rules

3. Requirements marked `JOB` need the test clock; those marked `LOAD` need the load environment; those marked `MAN` need a checklist with a recorded result.
4. The `S` and `C` requirements are tested when built, and tracked but not release-blocking.
